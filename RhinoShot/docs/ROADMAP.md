## مرحله‌ی ۲ — نمایش سه‌بعدی و ساخت مدل (مسیر الف: 3DMM)

### ۲.۱ نمایشگر سه‌بعدی داخل اپ ⬜
**کتابخانه:** Filament (`com.google.android.filament`) یا SceneView (`io.github.sceneview:sceneview`).
Filament سبک‌تر و برای موبایل بهینه‌تر است.

کارها:
1. افزودن وابستگی و یک `AndroidView` مبتنی بر `SceneView`/`ModelViewer`.
2. بارگذاری `model.glb` از حافظه‌ی محلی یا سرور + مدیریت چرخه‌ی عمر.
3. **کلید تعویض نما**: «مدل سه‌بعدی ⇄ ۹ عکس اصلی» — همان چیزی که در طرح خواسته شده.
4. چرخش با لمس، زوم با pinch، و نمای پیش‌فرض سه‌رخ.
5. نمایش مش قابل‌اعتماد: تعداد نقاط، بافت، و اینکه مدل از چند عکس ساخته شده.
6. اضافه کردن **خطوط اندازه‌گیری** (نازال، آلار، زاویه‌ی نازال) روی GLB — برای مشاوره.

**خروجی:** یک `Screen3D` که با `session.modelFile` کار می‌کند و اگر فایل نبود،
پیام «هنوز مدلی برای این جلسه ساخته نشده» + دکمه‌ی «ساخت مدل» نشان دهد.

### ۲.۲ ساخت مدل روی سرور (3DMM) ⬜
مدل‌های پیشنهادی: **FLAME** (چهره‌ی کامل) یا **DECA** (کیفیت بهتر بافت و مش).
مسیر پیشنهادی: **MediaPipe Face Mesh → پارامترهای FLAME → مش + بافت**.

خط لوله‌ی پیشنهادی (سرور، Python):
```
۹ عکس + session.json
   ↓  تشخیص چهره و تراز (align)
   ↓  تخمین پارامترهای FLAME (β, γ)
   ↓  بازسازی مش سه‌بعدی
   ↓  پروژکشن بافت از ۹ نما (ساده: انتخاب بهترین نما از روی زاویه‌ی
      نزدیک‌تر به زاویه‌ی هر vertex در فضای 3DMM)
   ↓  خروجی GLB + model_meta.json
```
* **مزیت:** ۹ عکس کافی است، سریع (کمتر از ۱ دقیقه)، حجم کم.
* **ضعف:** شکل دقیق بینی تقریبی است → برای تصمیم جراحی کافی نیست.
* **دقت مورد انتظار:** خطای نقطه‌ای حدود ۱٫۵–۳ میلی‌متر در برابر اصل؛ آن را
  در `model_meta.json` برگردانید تا پزشک بداند.

### ۲.۳ بک‌اند (Python/FastAPI) 🔄 طرح‌ریزی‌شده
```
app ──POST /v1/sessions/{id}/model──▶ FastAPI
                                       ├── تأیید توکن
                                       ├── ذخیره‌ی رمزشده‌ی عکس‌ها
                                       ├── enqueue (Celery/RQ + Redis)
                                       └── worker: FLAME/DECA ──▶ model.glb
app ──GET  /v1/jobs/{job_id}───────▶ وضعیت و لینک خروجی
```
* صف با Redis + Celery یا RQ؛ اگر ساده‌بودن مهم است: `arq` یا حتی یک صف
  مبتنی بر SQLite.
* رمزنگاری در حالت سکون: `cryptography` + AES-GCM، کلید از متغیر محیطی/KMS.
* لاگ دسترسی (چه کسی چه پرونده‌ای را دید) — الزام حریم خصوصی.
* حذف زمان‌بندی‌شده (مثلاً ۹۰ روز) با cron.

### ۲.۴ ابزار مقایسه‌ی قبل/بعد ⬜
* دو جلسه (قبل/بعد) را کنار هم بگذارید و مدل‌ها را با هم superpose کنید.
* نمایش اختلاف (مثلاً تغییر زاویه‌ی نازال) به‌صورت عدد + رنگ.
* ورودی: دو `session.json` + دو GLB.

## مرحله‌ی ۳ — مسیر ب: فتوگرامتری و دقت بالا ⬜

### ۳.۱ حلقه‌ی ویدیویی در اپ ⬜
* یک حالت جدید: «حلقه‌ی ۱۰–۱۵ ثانیه‌ای دور سر» با راهنمای زنده (سر در مرکز،
  سرعت چرخش یکنواخت، فاصله‌ی ثابت).
* استخراج فریم‌ها روی سرور با ffmpeg (هر ۳ فریم یکی) → ۴۰–۶۰ فریم هم‌پوشان.
* پیش‌نیاز: چرخش ۳۶۰° کامل، بدون قطعه‌قطعه شدن.

### ۳.۲ پردازش سروری ⬜
```
فریم‌ها → COLMAP (feature extraction, matching, SfM) → OpenMVS (dense) → GLB
```
* سخت‌افزار لازم: GPU (حداقل ۸ گیگ VRAM برای OpenMVS/Instant-NGP).
* زمان: ۵–۲۰ دقیقه برای هر بیمار → حتماً صف و نمایش پیشرفت لازم است.
* دقت: زیر ۱ میلی‌متر، قابل استفاده برای شبیه‌سازی.

### ۳.۳ دقت و کالیبراسیون ⬜
* برای اندازه‌گیری مطلق (میلی‌متر) به **کالیبراسیون مقیاس** نیاز است: یک
  مارک‌ر روی پیشانی یا یک خط‌کش مرجع در کادر.
* یا سنسور عمق (ToF / LiDAR) برای اسکن مستقیم.
* تا آن زمان، خروجی را با برچسب «تقریبی» نمایش دهید.
